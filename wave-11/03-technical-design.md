### 5.3 Selected Approach

- Selected: O-001, under every hard constraint, keeping the one delivered starter, the one delivered writer, the delivered timeline rule and the delivered assembly encode.
- Structural change:
  - Specification (D-001). Each item's graphic specifications live in a folder named graphics beside the item material file, one UTF-8 JSON file per graphic position, named after the position identifier the material records, lower-cased; code holds no identifier and derives the names from the material (M-016). A specification states its position, its beat, its row as a quotation of the shot list (equal to the material's quotation), the claims its row cites, its kind (still or motion) with a quotation of the owner's motion list, an optional disclosure quoting the owner's wording "schematic, not to scale", an optional seed, an ordered element list and, for motion, an ordered motion list. The closed element set, each subject-free: text (role title, label, caption, citation or figure; text, source path and quotation), point, bearing (a ray at a layout angle), path (polyline, smooth curve or closed loop), axis (label, no ticks unless quoted), trace (oscillation, near-linear or band form over an axis pair), angle (an arc between two directions with a label), region (sector, spread, cone, ellipse, band or box, shaded or outlined), panel (a framed sub-canvas for side-by-side layouts), blocks (an ordered box chain with arrows) and bars (extents with no values). The closed motion set: reveal (draw-on of named elements over a window), rotate (an element between two layout angles), sequence (sets of elements shown in turn), grow (a region parameter between two layout values) and follow (a marker moving along a path). Geometry is layout in frame units of the configured profile; a layout value that depicts a quantity is allowed only in a specification carrying the disclosure, or citing the owner answer that fixes it (the 60° case); a layout value carrying a shared name must be equal in every specification of the item naming it (the equal θ of graphics 5, 6 and 7). Every field is required unless the format marks it optional, and the drawing program fills no default: a missing field fails the render naming it.
  - The check (D-001, M-009). GraphicSpecificationCheck reads each specification's bytes once and hashes that buffer; it reads the shot list, claim record, narration and decision record as recorded, normalised as the delivered loader does (line endings only), and for matching additionally removes the Markdown emphasis characters asterisk and backtick from the source text. It refuses, naming the file and element: a missing, extra or duplicate specification against the material's graphics; a position, beat or row quotation that differs; a claim list that differs from the row's cited claims; a claim-record carried-by entry naming the graphic for a claim the row does not cite, unless the specification cites the owner answer resolving it (graphic 1 and claim one); a text element whose quotation is not found in its source or whose text differs from its quotation by any character; a figure not admitted; a quantity layout value with neither disclosure nor owner citation; a disclosure whose wording is not the quoted owner wording; an unknown element, motion or field; an undefined reference; motion in a still, no motion in a motion graphic; a shared layout value that differs; any address-like text (a scheme separator or protocol-relative prefix). The number rule: a figure is a text element containing a decimal digit or a word from the check's closed list of English cardinal and time-of-day words; a figure is admitted only when its quotation is found in the claim record (claim text or source column, which carries the citation years) or in a source a recorded owner answer admits, cited by the element; the check prints the item's figure set, which a test compares with the ruled set: 13–15 Hz, ~2 km, 60°, nine o'clock, noon and the end card's citation years.
  - Font (D-009, M-009). One face file, Inter Regular inside the verified font set, named by setting. Before any process, FontCoverage reads the face's character map (formats 4 and 12) from the very bytes the verifier hashed and refuses, naming the character, its code point and the graphic, any drawn character the face does not map; the font's family and version are read from its name table in the same bytes. The face reaches the browser only as the bundle's public copy, whose hash must equal the verified face's; every composition declares exactly that face under a family name read from the style file, with no fallback family; the composition waits for the face to load and fails the frame if it reports anything but loaded. Evidence that no system font drew a character is the coverage check plus the single declared family, as the Planning Gate ruled; no loaded-file record is claimed.
  - Render process (D-002, M-003, M-015). The repository folder graphics/ holds the render script (render.mjs) and the drawing program (drawing/, one root registering one generic composition taking its specification as input properties). IGraphicRenderer, realised by ExternalMediaTool, has two invocations, each starting the configured Node executable with the argument list [staged render script name, mode bundle or render, request file name] and no other argument, working directory the run's graphics staging folder, standard input redirected. The child environment is cleared and set to: SystemRoot and windir copied from the host; PATH set to the system directory only; TEMP, TMP, LOCALAPPDATA, APPDATA, USERPROFILE and HOME set to staging subfolders; TZ set to UTC; NODE_ENV set to production; nothing else. Before start, the starter refuses by name an absent or missing Node executable, render script, browser executable or face file. After start, the process is assigned to a new job object configured to kill every member on close, and only then is the start line written to its standard input; the render script reads that line before it loads anything. The render script loads the bundler and renderer through a require anchored at the installed folder's package.json, and imports nothing else beyond the file and path modules of Node. Bundle mode calls the bundler with caching disabled, root, output and public folders in staging, and an override resolving modules from the installed packages; render mode opens one browser with the configured browser path, selects the composition with the specification, style and timing as input properties, renders frames as PNG with the configured concurrency and per-frame timeout, writes them into a staging frames folder, closes the browser and exits. It never passes a licence key, never calls the still or media render functions and never calls the browser download functions. Exit codes: 0 done; 3 refused before the renderer was called (a missing file or an invalid request); 4 the renderer failed; any other code is a failure by name. Past the bound, or on cancellation, the job is closed, which ends every member; after any exit the job's active process count is read and the job closed, and a non-zero count is printed and recorded on the graphic's provenance.
  - Every write location of a render, each under the run's staging folder inside the output root: the staged render script, drawing program, style file, specification and request files (written by the one writer from the buffers hashed); the bundle output folder and its public folder; the operating system's temporary folder and the renderer's working folders inside it (browser profile, asset and compositing folders); the user profile folders the environment points at; the frames folder. Nothing is written under the installed renderer, browser, font or Node folders, nor in the repository; the before-and-after manifests and the verifier's no-extra-file check prove it (P-018).
  - Installation verification (D-003, M-008). The graphics settings name each manifest with its folder and its expected SHA-256 (from the decision record), the Node executable with its expected SHA-256 (the line its manifest holds), the browser executable and the face file as paths that must lie inside a verified folder. RendererInstallationVerifier reads files only: it hashes each manifest's bytes against the expected value and parses those bytes; it refuses an entry that is absolute or climbs out of its folder, a listed file that is missing or differs (naming both hashes), and any file under node_modules, the browser folder or the font folder that its manifest does not list (a re-created cache, a planted module); it verifies Node as one expected file; it reads the renderer's name and version from the verified bytes of the installed remotion package.json, the browser's version from the verified executable's version resource and the face's family and version from its name table. Hold: at Design's start every verified file is opened read-only with read sharing, hashed through its handle and held, with the staged inputs and, after bundling, every bundle file, until the last render process of the stage exits; a difference refuses naming the file and both hashes. The verify-graphics command and plan-only run the verification without the hold and start no process.
  - Order and stage form (D-004, M-005). After the version opens and the carried stages are recorded, the run executes Audio, then composes the timeline once with BeatTimeline.Compose over the measured beat durations and the visuals (graphics then clips per beat, as delivered) with planned relative paths, then Design, Thumbnail and Production; the assembly takes that same timeline. Stage-handler position, for the release record to quote: "The Design stage remains a step of the produce service, executed after Audio, and is not an IStageHandler, because a graphic render needs the run's measured beat durations, its staging folder, the one writer and the one process starter, none of which the contract's subject-only HandleAsync carries."
  - Output and assembly (D-005). A still graphic renders one frame (the specification's final state, independent of its span) to one PNG, recorded with role GraphicStill. A motion graphic renders exactly the frames of its segment; frame k shows motion progress at k over the motion window, whose length is the segment's frames times the style file's motion-end fraction (proposed 0.8), then holds the final state; the frames are promoted under the graphic's folder and a frame manifest (ordinal, relative path, length, SHA-256 per frame) is written by the writer and recorded with role GraphicMotion. Before encoding, the assembly re-reads every still and every manifest, re-hashes each against its recorded value and each frame against its manifest line, holds them all read-only until the encode exits, and writes the segment list: a still as one entry with its segment's duration, a motion graphic as one entry per frame with one frame's duration. The cumulative difference between the written durations and exact frame times is computed and the run refuses if it reaches half a frame. RenderAsync, its arguments and the total frame count are unchanged; graphic outputs alone are hashed and compared.
  - Reader pairs, every hashed input with the reader its hash names: the specification and the style file, hashed by the check over the one buffer read, staged by the writer from that buffer and held while the render script reads the staged copy (M-009, M-004, M-003); the render script and drawing program, read once, hashed, staged from the buffer and held while the bundler reads them (M-004, M-015); every installed file, hashed through the held handle while Node, the bundler, the browser and the compositor load it (M-008); the face, hashed in the verified set, its character map read from those bytes, and its bundle copy required equal before the browser loads it (M-009); every bundle file, hashed after bundling and held while the renderer's file server serves it (M-003); each frame and still, hashed by the writer at promotion, compared for sameness, listed in the manifest and re-hashed and held while the encode reads it (M-005); each final frame, re-hashed by the review command, copied by the writer with an equal hash and read by the sheet composition (M-014); each frame and still again re-hashed and held while the preview encode reads it (M-014); the approval file, hashed against its configured value and parsed from that buffer by the company plan (M-006); each manifest, parsed from the buffer hashed (M-008).
  - Provenance and sameness (D-006, M-001, M-012, M-013). Each graphic artifact is recorded with a graphic provenance row on the same short transaction: position, kind, specification path and SHA-256 (staged bytes), style SHA-256, drawing program and render script digests (staged bytes), bundle digest, renderer name and version, the four manifest hashes and verified file counts, Node and browser SHA-256 and versions, face family, version and SHA-256, segment start and frame count, frames rendered, first and last changing frame, final-frame SHA-256, frame-set digest, concurrency, the argument list and request-file SHA-256, observed render seconds, leftover process count and the sameness kind and statement. Sameness: on a demonstration store every graphic is rendered twice in separate processes and compared frame by frame, recording repeats with the digest or not observed to repeat with both digests and the first differing frame; on the company store each graphic renders once, each still's output hash is compared with the approved hash and a difference fails Design naming both, and each motion graphic records re-timed from this run's narration, not compared. The owner's approval is a JSON file the orchestrator writes under the company run folder, named by setting with its expected SHA-256: the date, the approver, the decision record entry described, the demonstration store and version, the sheet's and preview's hashes, the style file's hash, the four manifest hashes and, per position, the specification hash, the kind, the final-frame hash and, for a still, the still hash; a company-store plan refuses before any call when it is absent, differs from its expected hash, or names a specification or style hash that differs from the current file.
  - Review (D-007, M-011, M-014). review-graphics takes a production version of a demonstration store, refused by name on any other designation before any process; it re-hashes each graphic's recorded output, copies each graphic's final frame byte for byte into the review folder through the writer (role ContactSheetFrame), composes one sheet image with the media tool from those copies (22 tiles scaled to fit, four columns, each labelled with the position number and its row text quoted from the material, drawn in the approved face), records it (role ContactSheet) with the 22 final-frame hashes it was built from, and renders one preview video of the 22 graphics in position order at the production's recorded segment spans from the production's own stills and frames, video only, probed for one video stream and decoded with zero errors (role GraphicPreview). It prints every hash for the approval file. A version already holding a review set is refused.
  - Timeouts, holds and clocks (D-008). Every timeout, by name and file, with its value: datastore command timeout 30 s (the data library's default, F-036; src/MediaCompany.Persistence/NpgsqlUnitOfWork.cs), per short transaction only; probe 60 s, configured (ProductionSettings.ProbeBound), also the preview's probe; decode 60 min, configured (DecodeBound), also the preview's decode; still 60 s, configured (StillBound), also each sheet composition; render 60 min, configured (RenderBound), the assembly and the preview encode; model part 350 s and provider call 60 s unchanged; new installation hashing bound proposed 300 s, configured, over verify-graphics, plan-only and the Design-start hold (about 665 MB); new bundling bound proposed 120 s, configured, against 8.3 s measured cold (caching off makes every bundle cold); new per-graphic render bound, configured as a fixed allowance proposed 120 s plus a per-frame allowance proposed 0.5 s, applied to each render process separately (a still 120.5 s; the longest motion graphic with the previous narration 831 s against an estimated 154 to 204 s at the trial's rates); the renderer's fixed 25 s browser launch timeout and its per-frame readiness timeout passed explicitly as proposed 30 s (its minimum 7 s), both inside the per-graphic bound; concurrency proposed 1, the only value measured byte-identical (F-026), leaving the 22 logical processors unused for one render until a two-render comparison at a higher value is ruled; the start-line handshake, inside the bound. Holds: no transaction or datastore command is open during verification, bundling, rendering, frame promotion, hashing, sheet composition or the preview; each record is one short transaction after its file work; files are held read-only as D-003 and D-005 state. Clocks: every bound on the monotonic clock; render seconds observed with a monotonic stopwatch and printed as observed on this machine; every recorded instant the datastore's; the drawing program reads no clock (the frame index is its only time); the render script records no time. One pass with the previous narration is estimated at 13 to 17 min of rendering, twice in a demonstration run; an estimate from F-026 and F-017, never a measurement.
  - Network (D-010). Each path and its prevention: a browser fetch (the browser path is always passed and verified, the render script refuses a missing file, the download functions are never called); a usage event (no licence key; only the frame render function is called, which holds no licensing call, F-022); browser background services (the renderer's own launch flags, F-021, recorded as structural); assets by address (specifications and drawing program carry no address; the face is a bundle file); the excluded speech clients (never imported; the bundle is scanned and refused if it holds a module of theirs, A-011). Position: the renderer's file server serving the bundle and the browser's debugging port on loopback are inside the machine and are not network requests. Evidence: structural, recorded per render (arguments, request file, scans); observed in demonstration by sampling the operating system's connection table for the job's processes during renders, labelled sampled observation; no phase changes a security setting.
  - Boundary assertions (D-011, M-017): exactly one starter and one writer still, over the new types; no capability gateway or vendor adapter reachable from the drawing path; no subject term, item or position identifier in the drawing program, render script or style file, and no JSX text child or string literal outside the specification vocabulary in the drawing program; imports limited to react and remotion in the drawing program and to the anchored bundler and renderer plus Node's file and path modules in the render script; no licence key, still or media render call, browser download call, network API, clock read, random source other than the seeded one, raw-markup API or CSS animation in those sources; the review command's demonstration guard; tests needing the installed renderer are marked and skip naming why. Each fails on a seeded probe; every delivered case is unchanged.
  - Palette (D-012, M-016): the company style file config/graphics-style.json holds background #F5F1E8, line #1F2328 (14.01:1 on the background), secondary line #5F646B (5.29:1), accent #A8481A (5.17:1), text #1F2328 (14.01:1) and region shade #DEDCD5 (1.22:1 against the background; line on it 11.51:1, accent on it 4.24:1, secondary on it 4.35:1), with named stroke widths and type sizes and the motion-end fraction; the accent marks only an element a specification flags as its focus, carried also by a heavier stroke since accent and secondary differ by hue more than luminance (1.02:1), and never encodes a quantity or category.
  - Commands and settings (D-013, D-014, M-014): new verify-graphics (exit 0 verified, 2 refused naming every finding; starts no process); produce unchanged in options, with plan-only printing the graphics section; new review-graphics with --version (exit 0, 2 refused before any process, 3 a step failed); install --from 11. The graphics settings section: nodeExecutable (path, sha256), manifests (remotion, browser, font: manifest path, folder, sha256), browserExecutable, fontFace, renderScript and drawingFolder (repository-relative), styleFile (repository-relative), concurrency, frameTimeoutSeconds, bundleBoundSeconds, renderFixedSeconds, renderPerFrameSeconds, hashBoundSeconds, licence (value and source, printed as configured) and approvalFile (path, sha256; company designation only); each required where used, none defaulted in code.
- Rationale: O-001 is the only option satisfying every hard constraint with the smallest impact surface and the most reuse; the next-ranked survivors tie on impact and reuse and lose on quality attributes or operability.
- Highest-scoring rejected alternative and why it lost: O-007 ties O-001 on hard constraints, impact surface and reuse, and loses on quality attributes because the Design stage's record would cover only the ten stills and graphic provenance would be split between two stages.

  - Motion content keeps the delivered still-image encoder tuning (D-005).
  - Demonstration runs render every graphic twice (D-006).
  - Request-level network observation is replaced by structural evidence and a sampled connection table (D-010).
  - Three delivered live-test assertions follow the new order and roles (D-004).

## Operational Considerations

- Logging and observability updates: plan-only and produce print the graphics section (renderer, browser, Node and face identities with verified hashes and file counts, the licence as configured with its source, USD 0.00 planned, the bounds labelled configured, approval status in the company store); each graphic prints its specification hash, frames rendered, output or manifest hash, observed render seconds and sameness; review prints every hash for the approval file; no specification text beyond position identifiers, and no secret, is printed (M-005, M-006, M-014).
- Error handling strategy: a specification, coverage, verification or approval failure refuses before any call with exit 2 naming every finding; a render or bundle failure, a bound passed, a held-file difference, a bundle holding an excluded module, a still differing from its approved hash or a re-hash difference before assembly records the stage failed and exits 3 naming the file or bound and both hashes; operator cancellation closes the job and exits 6 as delivered (M-003, M-005, C-006).
- Security considerations: no network client, capability gateway or credential is constructed on the drawing path (C-007, C-009, M-022); the renderer receives explicit local paths and no licence key, and never fetches a browser (C-007); text reaches the browser only as text nodes (C-017); installed files are hashed and held against replacement and audited for extra files (C-004, M-008); the child environment is cleared so inherited variables cannot redirect what runs (M-003); nothing is distributed (C-008).
- Performance considerations: rendering is estimated at 13 to 17 min a pass from the trial's rates, twice in demonstration, unmeasured until P-018 (C-016, A-008); hashing about 665 MB and holding about 15,120 handles at each Design start (C-004); staging holds about 0.45 GB of frames a pass at the trial's frame size, cleared at the next run's start (M-004).
- Deployment and operability: the orchestrator applies the eleventh resource alone after a backup, writes the graphics section and the approval file outside the repository, runs verify-graphics and plan-only before the go (M-013, M-014, C-012, C-016).

3. Moving Design after Audio, as the gates require for motion, changes three delivered live-test assertions (F-029): the stamped order of the four produced stages, the count of 22 still artifacts (now ten stills and twelve motion manifests) and the interruption test's still file at graphic 5, now a motion graphic. 4. 5.
